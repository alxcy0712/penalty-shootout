# 《十一码之夜》成品质量研究与可行性路线

研究日期：2026-10-03。研究分支：`research/product-quality-roadmap-2026-10-03`。

## 结论先说

当前项目已经是一个规则与物理回归比较扎实、可本地续玩的点球游戏，不是只有画面的原型。与成品的主要距离，已经不只是“人物再细一点”：**输入尺度是否一致、异常时是否可靠、动作是否自然、制作流程是否可重复，以及真实手机上是否稳定**，比再堆材质或多跑同一批检查更重要。

本轮发现了新的可复现问题：校准与比赛使用不同高度归一化，同一手势的力度明显不同；拖动中仅布局位移就可能被当成射门；保存失败仍有“已经保留”的肯定提示。合并进 master 的 Blender 新流程还会重新改造现有成品模型，并在不兼容导出步骤前原地保存源文件。它们比增加多边形更值得优先解决。

推荐路线是：**先完成输入/保存/制作流程的可信度，再补真实浏览器与手机证据；随后用独立动画候选改善关键姿态，最后根据测量决定结构重整。** 不建议现在切换引擎、上全身物理/布料或承诺达到 FIFA/eFootball 的整体水平。可以借鉴它们的姿态、反馈和呈现标准，不能用两个运动员的点球项目推导同等规模的内容与技术能力。

本轮只分析与写报告，没有修改游戏逻辑、模型、动画或依赖，也没有部署。

## 1. 基线与证据可信度

已实时验证 master 为 `e1dcc3a06ac6513a9cc55be58004e29f2ee107df`，树 `320c9b8c73b66c599480ab3aeeb0cfa624cb8987`；其第二父提交是已交付 feature `3298648d77f03cd3d8f3e6329a392fb748184b75`，祖先关系成立。

合并后的差异只有四个 Blender 脚本，游戏运行时、测试和实际资产与已验收 feature 相同。因此可以引用最近 394 项测试、669 球 / 223 次接球的验收，但不能说它们验证了这四个新制作脚本。本轮重新执行构建和场景预算检查，另做针对性输入与 Blender 只读/内存探针。[基线与哈希](evidence/baseline.json)

本文使用三种证据等级：

- **已验证**：当前源码、实际文件或可重复的小探针直接支持；有些是代码行为，不代表已在手机观察到发生频率。
- **设计取舍**：实现符合当前意图，但还没有明确产品规格或用户研究支持。
- **待验证**：合理风险或候选改善方向，需要真实浏览器、设备测量或更多视觉比较，不能当成已发生故障。

当前没有新的 OOM、栈溢出或普遍崩溃证据；不能把“尚未真机测量”写成“手机一定卡”。同样，离线画面和几何通过也不能证明手机顺滑、操作直觉或动力学真实。

## 2. 优先级：先解决什么

P1 表示下一轮最值得处理；P2 表示随后改善；P3 表示只有产品方向确认后再投入。这里没有凭空设置“致命 P0”。工作量使用相对等级，避免用没有实现依据的精确天数。

| 优先级 | 问题与证据 | 玩家/维护影响 | 建议方案 | 规模与主要风险 |
|---|---|---|---|---|
| P1 | 校准框与比赛区域高度不同，120px手势在探针中约85.35%→31.02% | 校准失去直觉，玩家以为自己力度不稳定 | 统一物理像素/规范化尺度；为旧校准设置迁移或重新校准提示 | 小到中；需覆盖横竖屏、设备像素比和已有偏好 |
| P1 | 拖动中区域top改变80px，静止手指松开可触发约31.48%力度射门 | 旋转/浏览器UI变化可能误射 | 按一次手势固定坐标框，或布局变动明确取消手势并提示 | 小；真实系统浏览器行为仍待验证 |
| P1 | 存储失败后仍说“进度已经保留” | 玩家失去进度却被误导 | 成功/失败/不可用状态贯穿暂停与续玩；新比赛覆盖旧存档要可理解 | 小；不需要服务器 |
| P1 | 新 Blender 重建脚本不是当前资产的幂等入口，兼容性检查晚于源文件保存 | 维护者可能意外改坏制作源，无法复现已验收模型 | 单一候选构建入口、版本/插件预检、输入hash、临时输出、验证后原子替换 | 中；比继续雕刻更基础 |
| P1 | ≥250ms前台帧被profile排除；完整QA默认仍选旧manifest | “通过”和“流畅”的证据可能不覆盖真实问题 | 修测量定义、权威release清单、快慢门禁分层 | 小到中；不要把同一套跑十次当扩展覆盖 |
| P1 | 主游戏无应用层context-loss暂停策略；资源降级只写console | 黑屏/低模期间比赛可能继续，失败状态不清楚 | 显式加载/降级/恢复状态；故障注入与实机验证 | 中；Three内部恢复不等同比赛状态恢复 |
| P2 | 肘腕折角、袖口凹口、局部手套交叠仍在 | 近景暴露“拼出来”的关节形态 | 按关键姿态做局部拓扑/权重/法线候选，逐个验证；不再凭静态站姿接受 | 中；会影响接触表与物理结果 |
| P2 | 两段射手采集覆盖有限；门将比赛动作主要程序化 | 节奏/重心/手脚协同仍有机械感 | 增加少量真正有差异的动作源，按事件分段、支撑约束和版本化retarget | 中到大；许可、接触相位和骨架契约优先 |
| P2 | 冷加载、热机、GPU、内存和真实触摸没有完整设备档案 | 无法可靠选择画质/性能档位 | 建立真机矩阵与长局测试，再按瓶颈优化 | 中；目前不能预估最终手机FPS |
| P2 | 缺少解释结果与练习闭环 | 输球难区分操作、属性偏差和门将预判 | 可选练习模式、简洁射门反馈、确定性回放/重试 | 中；保持信息克制，不泄露AI未来选择 |
| P3 | 联机、长线养成、复杂裁判规则、完整足球赛 | 扩展目标用户与内容体量 | 先确认是否仍是轻量离线点球游戏 | 大/架构级；当前不是必须补齐的“bug” |

前六项收益主要来自可靠性与理解成本，不需要加实时渲染负担。后续动画候选应按视觉增益、接触一致性和运行成本一起决定，而不是靠测试数量证明“更像真人”。

## 3. 产品完整度：从能玩到愿意反复玩

### 3.1 首先让同一个操作产生可理解的同一种意图

力度校准问题有代码与数值复现，详见[产品/移动端审查](product-mobile-audit.md)。建议以实际手势位移与统一尺度定义“舒适满力度”，让校准和比赛共用同一个纯函数；不要分别读取两块高度不同的DOM后再各自归一化。迁移时应区分原始测量值和用户手动倍率，避免旧设置在新算法下突变。

布局变化期间，选择“固定本次手势坐标框”或“取消并提示重新滑动”都可行；前者更连贯，后者更容易保证不误射。必须测屏幕旋转、地址栏收缩、窗口resize、指针取消、按住后暂停与恢复，而不只断言结果是有限数值。

高级模式长按超过十秒、直到松手才触发超时，是现有回归测试保护的行为，不是本轮引入的错误。应明确究竟是倒计时宽限还是硬截止，并同步文案；改交互前不能只为了文字好看把已授权的手势打断。

### 3.2 反馈和训练比立即加入联机更划算

当前属性、心理、随机偏差和AI预判提供一定深度，但玩家未必能分清“我瞄偏”“力度过高”“球员属性产生误差”和“门将猜对”。优先增加结果反馈原型：显示玩家意图与实际球路、主要结果原因、是否门框/扑救后反弹；不要把所有内部参数铺满画面。

可行的练习闭环是固定球员/目标/seed的重复练习，再允许切换随机seed观察稳定性。回放可保存输入、seed、规则/资产版本及事件时间线，复用既有确定性采样；不要直接把当前可变Shot对象当作长期回放格式。验收需证明播放/拖动不改变比赛比分、RNG和下一脚，并区分物理钟与展示钟。

先用少量用户观察验证“能否解释刚才为什么没进”和“能否用反馈改善下一脚”，再决定是否做生涯、奖励或排行榜。没有留存实验，不能声称增加系统一定更好玩。

## 4. 人物、衣服和动作：哪些能小修，哪些需要换方法

详见[动作与资产审查](animation-assets-audit.md)。当前保护接触/支撑的解析约束是优势，应保留；但现有22根资产骨骼加2根运行时肩部辅助骨（总计24根）与线性蒙皮很难同时在所有极端姿态维持漂亮肘窝、袖口体积、抓握与起身形态。

近期两个模型候选已经说明：静态看更圆并不一定更好。一个候选的视觉收益太小，却改变接触与一次反弹进球；另一个权重候选在早期扑救变成明显扁切。它们被拒绝是正确结果，不能据此推导“再改模型没有办法”。下一步应以实际坏姿态的局部网格为对象，同时查看静态、最大屈肘、抬臂、贴身抱球和撑地，必要时调整关节环线和衣服厚度，而不是只移动外轮廓。

手部目前是带球体/地面约束的表面变形，已改善张开的四指和拇指尖，但不是独立手指骨骼，也不是完整拇指对掌。CMU 官方明确说明其手指/拇指是便利附加关节，运动并非真实采集，脚趾/手也可能有噪声；不能把它们当作高质量抓握来源。[CMU资料说明](https://mocap.cs.cmu.edu/)

可行选择：

1. **保持现有骨架，做少量离线纠正形状**：最适合近景折角/袖口；运行时按明确姿态参数混合，CPU审计与渲染必须用相同变形。风险是每个形状需覆盖球、地面和皮肤，不能只让截图好看。
2. **重新设计手/前臂局部骨骼或权重**：可改善多姿态表现，但突破当前24骨契约就需重新计算性能、绑定、碰撞与全部资产验证，属于独立重构候选，不是免费细化。
3. **引入新的真实动作片段**：优先填补缺失的低扑收球、起身、不同助跑意图；按“起步—支撑—触球—随摆—归位”事件对齐，不把统一全局smooth当自然化。能买到或下载到FBX不代表有再分发许可或能直接用。
4. **全身动力学/布料模拟**：目前不建议作为默认方案。它会增加调参、碰撞、确定性和性能负担；局部视觉纠正与更好的动作源应先尝试。

动作“软”不等于所有关节慢一点。真实感来自姿态的先后关系、速度变化、支撑接触和重心意图；脚掌几何靠近地面不等于已经证明承重。保留现在“几何支撑与物理力学不同”的标注，别把一个低高度数字当作自然起身的充分条件。

## 5. 性能与工程：不以画质换不可控开销

详见[工程/性能审查](engineering-performance-audit.md)。当前DPR上限、单阴影灯、模型/骨骼预算和共享资源已体现移动端约束，不应盲目推翻。最需要先修的是证据缺口：真实设备、异常恢复、加载阶段以及帧统计盲点。

官方建议支持这个顺序：Chrome明确指出桌面CPU节流不能复现手机架构，远程投屏本身也影响性能；Three.js资源计数不是GPU字节，GC也不会自动回收所有WebGL资源。[Chrome设备模拟的限制](https://developer.chrome.com/docs/devtools/device-mode) · [Chrome真机调试](https://developer.chrome.com/docs/devtools/remote-debugging/) · [Three资源清理](https://threejs.org/manual/pages/cleanup.html)

共享大包值得分析，但不是看到1.277MB就立即拆包。关键接触表在第一球就要使用，懒加载可能只是把等待推迟到出脚；Vite也已有异步依赖预加载优化。先记录首屏/首个可玩帧/首球、解析、解码和编译时间，再比较数据二进制化或按阶段预热。[Vite异步块加载](https://vite.dev/guide/features.html#async-chunk-loading-optimization)

现有两张人物纹理较小，不应直接上KTX2转码器或增大贴图。KTX2解决的是GPU纹理压缩，和传输gzip、网格meshopt不同；只有实际纹理内存/带宽成为瓶颈才值得试。[KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html)

## 6. 可执行路线与验收门槛

### 阶段 A：可信的操作和制作基础

范围：统一校准；拖动坐标连续性；保存失败/覆盖提示；主游戏加载与图形中断状态；修正profile与release验收入口；把新的Blender脚本改为候选构建流程。

退出条件：

- 同一手势在校准与比赛采用同一尺度，跨布局固定测试得到相同归一化输入；布局变化不产生无意射门。
- 存储失败可见且不谎报成功，旧进度覆盖是明确动作；坏存档可恢复到安全首页。
- 用 `WEBGL_lose_context` 在四个比赛阶段测试中断/恢复，比分和出脚不会暗中推进或重复。[规范与测试扩展](https://registry.khronos.org/webgl/extensions/WEBGL_lose_context/)
- Blender版本/插件/输入hash不符时在写文件前停止；所有候选先写新文件，成功后才提升。对同一输入的可复现性单独证明。
- 一条命令明确选669球/223接球或经过审查的新版本清单，串行重测输出放磁盘；不再默认悄悄跑早期525球。

建议第一批只做 A1：校准同尺度、拖动坐标、保存反馈/覆盖保护和候选制作预检；第二批 A2 再做测量入口、加载与上下文恢复。每批先完成独立回归再合并，基本不增加每帧渲染成本。没有必要同时更换动画系统。

### 阶段 B：设备与反馈闭环

范围：真实浏览器端到端、低/中/高档手机性能档案、冷网络/后台/图形恢复；练习与结果反馈原型。

退出条件：固定设备/版本/画布记录，至少十分钟重复对局，保留长帧与失败而非截掉；明确选定30或60FPS档位的目标，按P95/P99和输入延迟验收。FPS门槛是待产品确认的目标，不是当前已达到的承诺。静态预算继续守住18k/450KB/24骨；若实测必须调整，先提出准确代价再更改。

玩家能理解校准和失球原因，且反馈不遮挡瞄准/球门。练习与回放不会修改真实对局状态。此阶段也决定是否值得加难度/策略变化，而不是先堆模式数量。

### 阶段 C：有证据的动作与模型提升

范围：从最影响正常镜头的一个坏姿态开始，分别试局部拓扑/纠正形状和新动作段，保留被拒绝候选。

退出条件：同相机、同时间、正常速度与慢速的整段对照有明确可见收益；实际渲染变形进入皮肤/球/地面验收；两侧、目标极值、能力变化与加载/暂停/源切换都覆盖。原固定清单不删案例；几何改变的合法结果变化要解释，不能自动视为回归或自动重写golden。守住来源、触球事件、脚掌支撑和确定性；每个候选保留CPU和GPU实测代价。

只有局部方案多次失败且原因明确，再进入阶段 D 的骨架/动画数据架构重构。

### 阶段 D：可选架构重整

候选方向是统一“物理姿态、展示姿态、动画源、接触事件”的版本化契约，离线生成可审计的动作/碰撞数据，减少散布在多个文件的相位常数与模型假设。它应分模块替换并保留参考实现对照，不建议重写全部引擎。

联机需要服务器权威、同步/重放、防作弊和网络生命周期；完整足球赛还需要球员AI、导航与协作系统。这些是新产品，不是现有点球游戏小修的自然延伸，当前不进入实施计划。

## 7. 不应该从这份报告推出的结论

- 394测试通过不等于没有缺陷；本轮新探针已经找到原测试没覆盖的输入/反馈问题。
- 669球/223接球与采样皮肤零受保护穿插，不等于连续参数空间零穿插；早期手套和局部袖口接触仍有明确残留。
- 云端CPU微秒值不等于手机帧率，Blender离屏材质图也不等于浏览器实际成片。
- 未定义CI不等于远程没有任何外部服务；未定义dispose也不证明单例主场景已泄漏。
- 可编辑Blender文件存在不等于任意新版脚本能无损重建当前GLB；需要固定版本和候选流程。
- 这次没有实施上述修复。建议先批准阶段A的具体范围，再用阶段B的数据决定后续预算。

## 一手资料的用途与边界

以下官方资料在本轮由研究审查核对；它们支持方案原理，不替代当前游戏的实测。Three/Vite在线文档会更新，实施时仍须以package-lock固定版本和本地源码确认具体API。

- Chrome设备模拟与真机调试：支持“桌面节流不能等同真机”和测量时关闭投屏的建议，不提供本项目FPS结论
- Khronos WebGL上下文规范/扩展：支持可重复的图形中断注入，恢复是异步事件，不代表浏览器保证每次都能恢复
- Three LoadingManager、资源清理、GLTFLoader与KTX2Loader：支持加载状态、资源所有权和纹理压缩的方案；不证明当前存在泄漏或转码必然更快
- Vite异步块优化：解释懒加载依赖预取，拆包收益仍取决于首球何时需要数据
- CMU源数据说明：解释手/脚噪声和未采集的手指通道；Quaternius与Monteiro来源/许可按资产附录逐项区分在线核验与本地留存元数据
